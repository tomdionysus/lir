# Retained messages on Dagda's register map (2026-11-23)

A design for step 4's first noun, before any code. The rewrite's design gives
the shape ("Retained": Dagda's register map with expiry per key, wildcard
reads from each node's own view, the order stamp L1); the maintainer settled
L1 on 2026-11-20 (retained values order by (hlc stamp, node id)), which D6
carries. Dagda made D6 public on its develop (`00e0a9f`, contract version 3),
to ship in Dagda 0.5.0 with D5.

## Which noun each part is

| Part | Built on | Lir's own |
|---|---|---|
| Where retained values live | One Dagda register space, `lir/retained`, opened by every Lir node (`Context::registers().open`, HLC stamps, the default) | Nothing: no store, no replication, no merge |
| The order of two writes to one topic, on any nodes, across a split | D6's (hlc stamp, node id), the greater winning per key | Nothing |
| A retained message cleared by an empty payload | `RegisterOp::remove` (a tombstone, under the default window) | Nothing |
| Message expiry on a retained message | The register's expiry; `registers().now()` to count the interval left when sending | The 5.0 Message Expiry Interval, set from what is left |
| Retained messages sent at SUBSCRIBE | `registers().list(prefix)` at this node's view, the prefix the filter's literal front (`interest_prefix`), then `lir::mqtt::matches` | Retain Handling, Retain As Published, the grant check |
| A value larger than D6's 64 KiB | A Dagda object (`objects().write`), named in the register's refs, freed by the collector once no register names it | Nothing |
| Each Lir node running Dagda | `dagda::Node` on the node's Dannan node, in lir-node | Its settings (state, storage) under Dagda's names |

## What changes in MQTT's terms

- CONNACK says Retain Available 1 (omitted, its default).
- A PUBLISH with RETAIN 1 is delivered live as any publish, and committed to
  the space: a non-empty payload puts the topic's register, an empty one
  removes it [MQTT-3.3.1-5] to [MQTT-3.3.1-8]. At QoS 0 there is nothing to
  acknowledge, so the commit is not waited for by anyone; a commit that fails
  is logged and counted in the node's figures, never retried as a new write
  (it would carry a newer stamp than a later publish).
- The register's value is the PUBLISH as the publisher sent it (topic, payload,
  properties, and the publisher's client id), in Lir's own encoding, so a
  later SUBSCRIBE sends it with its properties.
- SUBSCRIBE: the retained messages matching each new filter are read from
  this node's view and sent with RETAIN 1, as Retain Handling says: at every
  SUBSCRIBE for 0, only for a subscription that did not exist for 1, never
  for 2 [MQTT-3.3.1-9] to [MQTT-3.3.1-11]. The grant's may_subscribe already
  held for the filter. `$` topics are not matched by a leading wildcard.
- A 3.x client: a retained PUBLISH is taken (no longer closed), and retained
  messages are sent with RETAIN 1 at subscribe.
- Live forwarding: the RETAIN flag is 0 unless Retain As Published
  [MQTT-3.3.1-12], [MQTT-3.3.1-13], as now.
- The Message Expiry Interval of a retained message sent at subscribe is
  what is left of it [MQTT-3.3.2-6]; one past it is not sent.

## What it acknowledges, and what it does not

- Nothing is acknowledged at QoS 0, so retained writes promise only what D6
  gives: the write is accepted on this node and reaches the others as heads
  exchange; across a split each side keeps its own latest, and the heal keeps
  the greater (stamp, node id). A retained read is this node's view, which
  may lag the cluster by the exchange's time: stated, not hidden.
- Waiting for "replicated" on a retained write is D2's per-space level, not in
  D6; QoS 1 retained publishes (PUBACK after replicated) wait for D9 and D2.

## Asked of Dagda (2026-11-23)

1. Tests: every Lir test runs on Dannan's simulated cluster (SimNodes on one
   World). Can a `dagda::Node` (or the heads and registers alone) run on a
   SimNodes node, with its custody and state, and is there a fixture for it?
2. A Lir node needs only head spaces. Must it open a DATA pool, and what is
   the least NodeOptions for a host that holds registers only?
3. A retained payload over 64 KiB: written as a Dagda object named in the
   register's refs, through the object store the contract has? Its size
   bound, and how a read fetches it.

## Dagda's answers (2026-11-23)

1. No SimNodes fixture today; every Dagda test runs real Dannan nodes on
   loopback. dagda::Node is built over a dannan::Context, so it could run on
   a simulated node that supplies a whole one: Dagda asks Dannan, and adds a
   fixture with 0.5.0's examples if it can. Lir writes no code until then,
   since every Lir test runs on the simulated cluster.
2. A node always opens its DATA pool today. Lir needs the full node anyway
   (see 3), so what it needs is the least settings for a DATA pool of one
   local directory with a size bound, which Dagda will give.
3. A payload over 64 KiB is written with `context.objects().write` (at the
   ack level needed), the register carrying a small value and refs = {the
   object's id}; the commit claims it; SUBSCRIBE reads the register, then
   `objects().read(id)`. The collector frees the object once no register
   names it (the register map's reachability; Dagda confirms the wiring for
   spaces opened through `registers()` before 0.5.0). No bound for Lir to
   state.

## Tests, named by what they prove

On the simulated cluster, as every Lir test:
- MQTT_3_3_1_5 and -6: a retained publish on one node is sent at SUBSCRIBE
  on another, with RETAIN 1; a new one replaces it.
- MQTT_3_3_1_7: an empty retained payload clears it; nothing is sent.
- MQTT_3_3_1_8: a non-retained publish leaves the retained one as it was.
- MQTT_3_3_1_9 to -11: Retain Handling 0, 1, 2.
- MQTT_3_3_1_12 and -13: Retain As Published.
- MQTT_3_3_2_5 and -6: an expired retained message is not sent; one sent
  carries what is left of its interval.
- After a split and a heal, every node sends the later of two writes to one
  topic (AthenaSIP's step 7, retained half).
- A late subscriber anywhere has every retained message under its filter
  (AthenaSIP's step 2).
